# Taste
- When extending the project with new content or features, prefers following the existing established pattern/structure (e.g. reusing the same YAML/component conventions) rather than inventing a new approach. Confidence: 0.5
- When changing behavior or restructuring a project, prefers deleting redundant/dead code (unused components, layers, branches, styles) rather than leaving it in place for minimal diff. Confidence: 0.6
- When mapping a ticket's service area, expects the full validity extent to be covered (including secondary/rail-only extensions beyond the primary boundary) instead of being left as a documented gap or draft note. Confidence: 0.5
- Wants map markers to degrade progressively as the user zooms out: full label + icon at high zoom, icon only at mid zoom, and fully hidden at low zoom. Confidence: 0.55
- Prefers UI built from @material/web's existing components and design tokens instead of hardcoded values (hex colors, raw font stacks, fixed sizes); wants existing hardcoded CSS progressively tokenized. Confidence: 0.7
- Wants app icons to reproduce the operator's official app icon (real branding) rather than a neutral, trademark-avoiding placeholder. Confidence: 0.7
- Wants a ticket/app service area defined by the network's actual operational reach (the locations of every bus stop and rail station it serves) rather than by an administrative boundary. Confidence: 0.65
- Prefers square (right-angle) corners over rounded ones on UI surfaces such as the info panel — corrects rounded borders to `border-radius: 0`. Confidence: 0.6
- For a fare with no single price, prefers a short plain-language summary of the billing/charging rules instead of a "View fares" link out to the operator's site. Confidence: 0.6
- Wants list rows (e.g. ticket entries) to be interactive only when there is more detail to reveal; entries whose only value is a single price should render as plain, non-clickable rows with no chevron. Confidence: 0.55
- Expects text inside a card to wrap within the card's bounds — content must never spill outside/overflow the card horizontally. Confidence: 0.5
- Wants project content/data structured to scale to multiple countries — a top-level country layer in the content folders, and records/scopes named and reviewed for country consistency — rather than left single-country-specific. Confidence: 0.5
- Wants the home/index map to surface every mapped country at once (drawing all apps) rather than featuring a single country's map, so each country appears on the landing view as soon as its records exist. Confidence: 0.65
- Wants an app's overview area drawn as one single unified region (e.g. the whole country in one color), with each product's narrower range (e.g. individual City Pass extents) revealed only when that product/ticket is selected — instead of drawing all sub-areas together at once as a multi-colored patchwork. Confidence: 0.6
- Wants selecting an extent on the map (clicking a region area or opening a product/ticket with a coverage range) to recentre the map on that extent's centre while keeping the current zoom level unchanged — explicitly asked to remove the auto-zoom and keep only the centring move. Confidence: 0.65
- When compiling lists of apps/services, expects entries filtered strictly to those that genuinely meet the stated capability criterion (e.g. can buy the regional/period pass inside the app itself), with non-qualifying entries dropped rather than listed with caveats. Confidence: 0.5
- For regional transport/app roundups, wants metropolitan-area operators and regional-level operators listed together in the same answer (only truly nationwide apps excluded), rather than restricting the scope to urban/metropolitan areas alone. Confidence: 0.6
- Wants the assistant to actually carry out real file/repository operations (editing, building, verifying) rather than stopping at a proposal or description of what could be done — expects explicit opt-outs when a task should stay research-only. Confidence: 0.6
- Avoids dead-end placeholder UI: when a panel section has no list items (e.g. an app with no ticket records), it should offer a working link out to the relevant operator page — with the section heading itself becoming the clickable link — rather than leaving bare placeholder text with nothing under it. Confidence: 0.6
- Wants each app's listed transport modes limited to those that actually exist in its service area (bus, tram, commuter ferry, rail station, etc.) — a mode that the operator does not run should be omitted rather than mentioned. Confidence: 0.5
- When classifying a network as "integrated", counts a single-mode (bus-only) network as qualifying — prefers such cities listed together with multi-modal ones rather than dropped for lacking mode diversity. Confidence: 0.55
- Wants an app's map marker/icon to be a click target equivalent to its coverage area (open the app's panel and focus/recentre on its range), so an app whose area is buried under another's stays selectable. Confidence: 0.5
- Expects a coverage area's boundary to be derived from the fare authority's published zone map plus the actual extent of the stops/modes the app supports (bus, tram, commuter ferry, rail stations) — rejects rough bounding-box shapes that look blocky and spill into neighbouring countries/regions. Confidence: 0.6
- Wants the operator's zone map treated as the primary reference for an app's coverage area, with the union of the stops/modes it actually serves (bus, tram, commuter ferry, rail stations) used only as a fallback when no zone map exists — the priority is explicitly zone map first, stop coverage second. Confidence: 0.6
- Treats UI/interaction performance as a first-class concern: flags lag once the map renders a large number of app coverage areas at once and wants the load reduced (rendering/data/architecture) rather than accepting the slowdown. Confidence: 0.5
