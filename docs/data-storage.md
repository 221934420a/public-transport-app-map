# Storing and managing map shell data

Short answer: **yes, YAML is a good fit for the map metadata and region
definitions, but not for large coordinate arrays.** Use YAML for the editable
records and GeoJSON for geometry. This project already uses that split.

## Recommended split

| Data | Storage | Why |
| --- | --- | --- |
| Map shell settings (title, view, marker, colours, copy) | YAML content collection | Small, human-editable, validated by Zod, hot-reloaded in dev. |
| App icon artwork | SVG markup in an `icons` YAML record | Keeps `AppIcon.astro` generic; one file per app icon. |
| Apps, tickets, service-area metadata | YAML content collection | Readable diffs and references by stable IDs. |
| Region polygons, boundaries, routes | GeoJSON under `public/geo/<country>/` | Standard GIS format; can be opened in QGIS, geojson.io, or generated by a script. Referenced by `geometry_refs`. |
| Very large geometry sets (thousands of features / MBs) | PMTiles or vector tiles generated at build time | The browser only downloads visible tiles instead of one huge GeoJSON file. |
| Source-of-truth relational data / imports | SQLite or Postgres during the build step | Query and validate records, then emit YAML/GeoJSON or tiles. Not shipped as-is. |

## Why not put everything in YAML?

YAML is excellent for labels, numbers, colours, and references. It is poor for
polygon coordinate arrays because:

- a single boundary can contain hundreds of thousands of numbers;
- large YAML files are slow to parse and painful to review in a diff;
- GIS tools work with GeoJSON, not YAML;
- every map visitor would download the whole data file even if they only need one region.

Keep each GeoJSON file focused on one meaningful boundary or layer. A service
area can reference several files and supports a feature fragment:

```yaml
geometry_refs:
  - /geo/united-kingdom/greater-manchester.geojson#greater-manchester
  - /geo/united-kingdom/bee-network-anybus.geojson
```

The part after `#` selects `feature.id` or `feature.properties.id`. If the whole
file is the boundary, omit the fragment.

## One file per record

`src/content.config.ts` uses Astro's `glob()` loader for every collection:

```ts
loader: glob({ pattern: '**/*.yaml', base: './src/content/coverage' })
```

Coverage and ticket records are grouped by country, for example
`coverage/united-kingdom/`. The loader still treats every YAML file as its own
record, and the record's `id` field (not the folder path) is the stable ID.

This scales better than a single file containing an array of records:

- adding an app or service area means adding one file, not editing a growing array;
- merge conflicts are limited to the record that changed;
- filenames and IDs stay easy to audit;
- the schema validates every record at build time.

A service area lists its own `geometry_refs`, so showing a new block only means
adding a coverage record for that app. The map draws every service area whose
`app_id` matches its app; there is no separate list of coverage IDs to edit.

## How much is too much?

For this project's scale (tens of apps, hundreds of tickets and regions), YAML +
GeoJSON is fine. Watch for these signals:

- a GeoJSON file is several megabytes and is slow to parse;
- the map loads geometry that is outside the current viewport;
- many regions need to be queried or filtered by attributes;
- the number of files makes authoring hard.

Before reaching for tiles, shrink what already ships: `npm run geo:simplify`
trims vertices and coordinate precision from every file under `public/geo/`
(see the README), which usually buys an order of magnitude.

At that point, keep YAML as the small index and move geometry to PMTiles/vector
tiles. The YAML record can store a tile layer ID or URL instead of a GeoJSON path.
The map component only needs a small adapter that reads that field and calls
`map.addSource` with a `vector` source.

## Validation

Run:

```sh
npm run build
```

Astro validates every YAML record against `src/content.config.ts` before
generating the site. A missing field, invalid URL, or wrong type fails the build
with the file name and field path, which is much safer than untyped JSON or
hand-edited arrays.
